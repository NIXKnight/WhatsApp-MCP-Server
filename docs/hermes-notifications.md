# Incoming-message notifications and persistent Pi sessions

**Installation and deployment remain PAUSED.** This document does not authorize service activation, migration execution, database access, backlog mutation, model prompting, ordinary MCP child startup, or a WhatsApp action. The sole exception is a separately and explicitly operator-invoked `--check-pi-inventory` command: that invocation authorizes configured auth/model reads and provider/model selection plus one owned temporary, isolated MCP inventory connect/bind/dispose cycle using validated command/args/cwd. Its public-interface loader uses only owned temporary cwd, agentDir, and HOME/.agents resource roots, restores HOME exactly after disposal, and contains only the owned MCP built-in and WhatsApp registration; configured project/agent/global extensions/skills/templates/themes/context/system files/hooks and unrelated MCP servers cannot be scanned, loaded, or run, and no prompt/tool/action/output is authorized. The check is mandatory before a separately authorized schema-v2 cutover. The session controller accepts only authenticated schema-v2 events after that clean cutover. The target inventory is 8 services, 26 bridge HTTP routes, 21 MCP tools, and 11 migration pairs through `000012` (with no `000002`). Section 14 remains binding: the existing bridge and existing WhatsApp MCP are reused and no replacement gateway/Reactor/action authority is introduced.

## What is notified

A schema-v2 event adds canonical chat identity, sender identity/alias, chat kind, own-account origin, and a bridge-assigned per-chat sequence to the existing metadata-only event. Bridge ingestion order is authoritative; the controller never processes sequence N+1 before N. Manual own-account messages may start Pi, confirmed Pi-originated callbacks are context-only, and unresolved own-origin mutations pause only that chat. History/recovery imports, unsupported empty messages, edits/revokes/pins, disallowed chats, and duplicate row updates remain excluded.

The wire contract contains `schema_version` 2, event type/ID, message ID, timestamps, `chat_sequence`, sender and optional alternate sender JIDs, `is_from_me`, `chat_kind`, source `chat_jid`, and `canonical_chat_jid`. It contains no message text, preview, display name, filename, media URL/key, credential, signature, or configured endpoint. Retries preserve body bytes and event ID while using a fresh signing timestamp.

### Identifier privacy is not anonymity

A native direct-chat JID commonly contains a phone number; group and LID JIDs
and message IDs are also correlatable identifiers. Removing a separate sender
field does not remove this inherent disclosure. Existing `get_messages(jid)`
requires the native chat identifier. This feature deliberately adds no opaque
reference adapter or Python tool. Obtain consent for these identifiers; prefer
group-only allowlists when direct-chat phone disclosure is unacceptable, or
leave notifications disabled. Hermes can retrieve message content through
explicitly permitted MCP tools, so metadata-only delivery does not mean the
receiver can never see content.

## Configuration

All settings are startup environment settings; changing policy requires a
graceful restart. There are no new CLI flags. Use the operator-managed existing
secret environment source, never an inline secret argument, committed file,
or copied example credential. No credentials are generated by this feature.

| Variable | Default / requirement |
|---|---|
| `BRIDGE_MANAGED` | `false`; exact lowercase boolean; managed mode never emits a QR |
| `BRIDGE_NOTIFY_ENABLED` | `false`; strict boolean |
| `BRIDGE_NOTIFY_URL` | Required when enabled; full `/webhooks/<route>` endpoint |
| `BRIDGE_NOTIFY_SECRET` | Required when enabled; at least 32 bytes of operator-provided HMAC key material, never logged |
| `BRIDGE_NOTIFY_GROUP_ALLOWLIST` | Required when enabled; exact comma-separated canonical numeric `@g.us` JIDs |
| `BRIDGE_NOTIFY_OPERATOR_JIDS` | Required when enabled; exact comma-separated operator PN/LID aliases sharing one private session |
| `BRIDGE_NOTIFY_TIMEOUT` | `5s`; 1ms–30s |
| `BRIDGE_NOTIFY_POLL_INTERVAL` | `1s`; 100ms–1m |
| `BRIDGE_NOTIFY_MIN_INTERVAL` | `2s`; 100ms–1m, global spacing between attempts |
| `BRIDGE_NOTIFY_BATCH_SIZE` | `20`; 1–100 attempts per cycle, one in flight |
| `BRIDGE_NOTIFY_MAX_ATTEMPTS` | `10`; 1–100 committed claims, including interrupted claims |
| `BRIDGE_NOTIFY_MAX_AGE` | `24h`; 1m–7d from original receipt, frozen per event |
| `BRIDGE_NOTIFY_RETENTION` | `7d`; 1h–30d after terminal transition |

No wildcard/all-inbox option or bare-number normalization is available. Invalid
enabled settings fail startup with fixed errors, without echoing input values.
Operators must supply high-entropy authentication key material of at least 32
bytes; validation counts bytes, not characters. The receiver's unauthenticated
test sentinel is rejected; there is no insecure bypass or generated key.

HTTP permits only a literal loopback IP. HTTPS requires normal certificate
validation and a loopback/private destination. At dial time every DNS answer
must be permitted; mixed private/public answers fail closed. IPv4-mapped IPv6
is normalized, and public, unspecified, link-local/metadata, multicast, and
zoned addresses are rejected. The connection is made to the exact validated
numeric IP without a second DNS lookup; HTTPS keeps the original hostname/SNI
and certificate verification. A shared normalized admission check also explicitly
denies the AWS IPv6 metadata endpoint `fd00:ec2::254` before ULA admission.
RFC1918 IPv4 and other ULA IPv6 are supported private ranges; public and CGNAT
destinations are not. Proxies, redirects, URL userinfo,
query strings and fragments are prohibited. Bare default-profile webhook paths
are supported; multiplexed profile URL prefixes are not implemented.

## Receiver and Pi capability gates

Hermes remains an external receiver option, not an authorization boundary. For any Hermes route, resolve and inspect its effective tools; deny terminal, shell, browser, filesystem, generic network, delegation, and WhatsApp mutation tools unless separately authorized. Empty or misspelled toolsets are not deny-all. Retrieved WhatsApp content is untrusted input.

The persistent controller preserves configured Pi capabilities and adds the existing 21-tool WhatsApp MCP inventory through its pinned `pi-mcp-adapter` dependency. The controller owns one isolated in-memory adapter snapshot for WhatsApp; it does not merge ambient adapter MCP server configuration, while normal mode retains other configured Pi packages/extensions after removing only the exact adapter package declaration from that loader's effective settings. Its system prompt is behavioral policy, not process/network isolation. Before activation, review operator templates, model selection, exact group/operator IDs, approval boundaries, and all 21 tools. Both operator preflight and first-turn readiness collect every tool whose qualified name starts with `mcp__whatsapp_session_controller__` and require that multiset to equal exactly the 21 production-derived names, with unique cardinality, direct exposure, exact adapter source path `<inline:mcp>` plus source `inline`, and all 21 exact names active; hidden, inactive, missing, duplicate, extra 22nd, same-name shadowed, or wrong-provenance tools fail closed before prompt. Generic `mcp`, `mcpScript`, and per-server namespace proxy tools must not be active or callable; a generic gateway may remain registered only while inactive and non-callable and does not count. The preflight uses in-memory settings and only the controller-owned adapter factory and WhatsApp snapshot, never loads or runs project/agent configured extensions, startup hooks, skills, templates, themes, context, or unrelated MCP servers, never relays child/startup stdout, and never prompts or executes a tool. On bare metal, the bridge, MCP server, embedder, transcriber, and dashboard units still read `~/.config/whatsapp-bridge/env`; this is transitional shared compatibility configuration until a later migration. Its exact accepted current-consumer union is `DATABASE_URL`, `PG_DSN`, `BRIDGE_ADDR`, `BRIDGE_DATA_DIR`, `BRIDGE_LOG_LEVEL`, `EMBEDDER_URL`, `ANALYZER_URL`, `MEDIA_RETRY_ENABLED`, `MEDIA_RETRY_INTERVAL`, `MEDIA_MAX_DOWNLOAD_ATTEMPTS`, `MEDIA_RETRY_BATCH_SIZE`, `BRIDGE_URL`, `LOG_LEVEL`, `MCP_TRANSPORT`, `MCP_HOST`, `MCP_PORT`, `WORKSPACE_DIR`, `WORKSPACE_HOST_PATH`, `EMBEDDING_MODEL`, `EMBED_BATCH_SIZE`, `EMBED_POLL_INTERVAL`, `EMBED_HTTP_ADDR`, `WHISPER_URL`, `TRANSCRIBE_BATCH_SIZE`, `TRANSCRIBE_POLL_INTERVAL`, `ANALYZER_HTTP_ADDR`, `DASHBOARD_HOST`, `DASHBOARD_PORT`, and `CONFIG_PATH`; private bridge-only `~/.config/whatsapp-bridge/relay.env` owns `BRIDGE_NOTIFY_ENABLED`, `BRIDGE_NOTIFY_URL`, and optional documented delivery tuning; shared `~/.config/whatsapp-notifications/env` owns only `BRIDGE_NOTIFY_SECRET`, `BRIDGE_NOTIFY_GROUP_ALLOWLIST`, and `BRIDGE_NOTIFY_OPERATOR_JIDS`; and `~/.config/whatsapp-session-controller/env` is controller-only. The bridge retains compatibility+relay+shared files and launches through exact `/usr/bin/env BRIDGE_ADDR=127.0.0.1:8080 BRIDGE_LOG_LEVEL=info` assignments in `ExecStart` before the bridge binary, so managed loopback/info are authoritative while documenting that `EnvironmentFile=` values override `Environment=` assignments regardless of directive order. The controller reads shared+controller only and applies `UnsetEnvironment=DATABASE_URL`. All managed directories/files are operator-private (`0700`/`0600`), symlink/non-directory and symlink/non-regular paths are rejected, existing content is preserved, values are never printed, and the controller never receives `DATABASE_URL`. Startup listens with intake unready and waits abortably for strict bridge `CONNECTED`/`is_connected=true` status before scheduler start; it does not start Pi/MCP while waiting. Once ready, the controller continues probing the same strict status contract. One timed-out, failed, non-OK, malformed, or non-exact operational probe immediately drops readiness, fail-closes the coordinator application fence and heartbeat, makes already-claimed pre-prompt workers observe `appCurrent=false`, requests exit 1, and enters the same cleanup path without issuing another Pi prompt. Normal signal shutdown retains graceful scheduling stop and unbounded drain. First claimed work validates the inventory before prompting.

## Delivery, expiry, and failure behavior

The dispatcher is independent of the WhatsApp callback and store writer. It
commits one exclusive lease before HTTP and never holds a SQL transaction over
network work or waiting. Updates are fenced by event ID, lease token, state,
and unexpired ownership using PostgreSQL's execution wall clock (not an app
timestamp sampled before queue admission). Expired leases recover on bounded maintenance.
Claims consume attempts even when a crash prevents transmission. Database
operations have 2s deadlines; HTTP has the configured timeout and event expiry
deadline. Cancellation, callback removal/draining, worker waiting and store
closure are ordered on all startup/signal/error exits.

Each POST supplies stable `X-Request-ID`, fresh Unix-second
`X-Webhook-Timestamp`, and lowercase hex `X-Webhook-Signature-V2`, computed as
HMAC-SHA256 over `<timestamp>.<raw-body>`. Hermes allows ±300 seconds clock
skew; maintain synchronized clocks. No legacy authentication fallback is used.

- `202 accepted/coalesced` and `200 duplicate`, with a matching delivery ID,
  record **receiver acceptance, never agent completion**.
- `2xx ignored` is terminal ignored work, not success or repeated delivery.
- Timeouts/reset/transient network errors, 408/425/429 and 5xx retry.
- Redirects, other 4xx, invalid certificates and destination-policy failures
  terminate. Fix authentication/route/capability issues operationally; dead
  letters do not automatically replay.
- Missing, mismatched, malformed or oversized success acknowledgements retry
  as ambiguous protocol failures. Responses are bounded to 8KiB and never
  logged/persisted.
- Backoff grows from 5s to a 5m cap with bounded jitter. Both numeric and date
  `Retry-After` are honored; 429 also cools down the route in memory. This
  route cooldown is not durable across restart. A retry requested beyond the
  event's remaining lifetime expires it rather than violating `Retry-After`.
- Age/attempt exhaustion produces dead letters. There is no replay API.

If Hermes accepts but the bridge crashes or cannot commit its acknowledgement,
the same ID may be sent again. Hermes' one-hour in-memory duplicate cache is
not durable and is not exactly-once protection. Restart/cache expiry can permit
another run; acceptance/coalescing may also be followed by receiver/agent
failure with no run completion. Finite retry/expiry bounds mean delivery is not
guaranteed through arbitrary outages. In-flight requests or already accepted
runs cannot be retracted by disabling the bridge or retiring an outbox row.

Disabled configuration reads neither destination nor secret, makes no delivery
attempts and creates no new events. Existing pending work remains parked until
expiry or explicit retirement. Cleanup runs at startup and once per minute,
in batches of at most 250 transitions and 250 terminal deletions, even while
delivery is disabled. Disabled mode ignores other notification environment
overrides and uses the maintenance defaults (7d retention). Re-enabling sends
only unexpired pending events allowed by the current policy; removed chats are
retired. No history/disabled-period backfill occurs. Dead/ignored/accepted rows
are never automatically requeued.

Expiry blocks new delivery at claim/attempt time. Retention deletion is batched
maintenance, not an instantaneous hard deletion SLA: a large backlog, database
failure or stopped/PAUSED process can delay cleanup. When restarted, stale work
still cannot be delivered. For stricter deletion requirements use the separately
authorized purge procedure below. Worker memory/concurrency is bounded, but
outbox disk capacity still requires operator monitoring. New relay logs use
fixed classes and opaque event IDs only; existing bridge ingestion logging is
unchanged and may contain WhatsApp data.

## Mandatory clean-cutover gate

Schema-v1 pending/leased work has no trusted per-chat sequence and must not be replayed. Keep delivery disabled and prior relay workers stopped. Through a separately authorized database-administration channel:

1. Review only v1 state aggregates and opaque IDs first.
2. Select retain, expire, or retire under the approved retention policy.
3. Obtain separate write authorization before any state change.
4. Execute the approved external runbook; repository installers and lifecycle targets contain no destructive retirement action.
5. Recheck that no unintended v1 pending/leased work remains.
6. Verify exact allowlists, endpoint/authentication, normal controller readiness, and effective receiver capabilities.
7. With delivery still disabled, explicitly invoke exact `BRIDGE_NOTIFY_ENABLED=false docker compose run --rm --no-deps session-controller --check-pi-inventory`; require stdout `{"status":"pi_inventory_ready"}` and exit 0. This authorizes only temporary auth/model reads and the isolated owned-resource MCP connect/bind/dispose; configured extensions/hooks/servers stay inert, with no child/startup output, prompt/tool/WhatsApp/Redis/database/backlog activity.
8. Obtain separate activation approval before enabling v2 delivery.

No SQL is embedded here because review and retirement remain documentation-only gates until separately authorized. Queue retirement cannot retract a receiver acceptance or WhatsApp action already performed.

## Migration and rollback safety

Migration 012 is additive for messages, identifies old v1 rows, and adds v2 ordering state. Starting a migration-aware bridge can apply it, so binary start/restart is an authorized deployment action. Routine rollback disables delivery, drains/stops the controller, and retains PostgreSQL, Redis, and Pi session state.

The down migration destroys v2 ordering metadata and requires separately authorized downtime. Redis namespace deletion, Pi-session deletion, v1/v2 queue deletion, forced schema metadata changes, and forced controller termination are destructive and absent from install, setup, start, stop, deploy, and routine rollback automation.

## Controller startup, durability, and shutdown

Bare-metal controller commands accept only exact Node.js `22.19.0` or `24.12.0`; the container retains its `22.19.0` baseline. The webhook listener starts with readiness false. The controller polls only the validated literal-loopback bridge base URL and requires the exact live status contract (`state=CONNECTED` and `is_connected=true`) before starting the scheduler or advertising readiness. The status `state` remains the state-machine value; `is_connected` independently reflects live underlying WhatsMeow `IsConnected() && IsLoggedIn()`, so divergence fails the strict startup contract. SIGINT/SIGTERM aborts this wait and enters the same cleanup path. Poll failures and malformed status bodies are not logged, and Pi/model/MCP initialization remains lazy and cannot occur during this normal startup wait; `/ready` excludes Pi. The operator-only inventory command is a separate direct CLI mode that constructs no listener, Redis, bridge probe/event, mapping, scheduler, or webhook and cannot prompt or call a WhatsApp tool. While operational, an abortable periodic monitor applies the same exact contract fail-closed: one timeout, transport failure, non-OK response, malformed body, or non-exact status synchronously drops readiness, invokes idempotent coordinator `failClosed()` before `requestStop(1)`, aborts scheduler plus application heartbeat, makes active workers' `appCurrent()` false before prompt, emits only the fixed deduplicated `lease_lost` terminal diagnostic, and enters cleanup. Stop/signal aborts and settles the monitor through ordinary graceful `stopScheduling` and unbounded drain without invoking fail-closed loss. For bare-metal deployment, notification auth/admission lives only in `~/.config/whatsapp-notifications/env`; relay activation/tuning lives only in `~/.config/whatsapp-bridge/relay.env`; the transitional shared compatibility file admits only the exact 29-name current-consumer union documented above until a later migration; the controller file is controller-only, and the controller unit never reads either bridge file.

Redis 7.2+ must report AOF enabled, `appendfsync always`, `noeviction`, and successful `WAITAOF` before intake acknowledgement. Production Compose Redis has no host-published port and is attached only to the dedicated internal controller network; the controller joins that network plus `default`, the namespace-sharing bridge inherits both, and unrelated MCP/enrichment/dashboard services do not join the controller network. `protected-mode no` is limited to that internal network. Bare-metal systemd instead executes the preserved `redis.conf` followed by fixed `--bind 127.0.0.1 ::1 --protected-mode yes`, so final command-line precedence prevents preserved configuration from exposing Redis. Redis stream state, Pi JSONL sessions, and PostgreSQL cover different durability boundaries; they do not prove universal zero loss under host loss, storage corruption, forced termination, or failover.

Compose uses raw `${POSTGRES_PASSWORD:-whatsapp}` only for PostgreSQL initialization and percent-encoded `${POSTGRES_PASSWORD_URI:-whatsapp}` in every client DSN. The URI variable must encode the same initialized raw password. An existing volume retains that credential; changing either variable does not rotate the role. Rotation remains separately authorized and verified before both matching representations and client DSNs change. Repository documentation contains no executable destructive SQL.

The shared Pi SDK loader and model runtime initialize lazily once, while each active turn owns and disposes its own `AgentSession` and keep-alive stdio MCP child. On SIGTERM the controller closes intake, stops scheduling, waits indefinitely for those active Pi turns and their MCP children, then independently attempts HTTP, Pi-session, repository, and Redis cleanup before computing its final exit code and emitting `stopped`. Systemd gives the bridge a non-propagating `Wants=` relation to the controller plus `Requires=` on Redis, so explicit controller stop leaves the bridge available for drain, and uses an infinite controller stop timeout. The Redis unit's post-config `--bind 127.0.0.1 ::1 --protected-mode yes` arguments are mandatory final overrides. The bridge unit sets `BRIDGE_MANAGED=true`, `RestartPreventExitStatus=78`, `StandardOutput=null`, and `StandardError=journal`, retains compatibility+relay+shared files, and uses exact `ExecStart=/usr/bin/env BRIDGE_ADDR=127.0.0.1:8080 BRIDGE_LOG_LEVEL=info %h/.local/bin/whatsapp-bridge`; managed mode never generates a QR, discards SQL-store/migration and WhatsMeow adapter details from construction onward without buffering/replay, and exposes pairing/permanent failure only through application fixed classes. The events-layer calls the terminal handler first and emits fixed `permanent_disconnect` exactly once for its winner in managed mode, where permanent reason/message/code/expire values are prohibited; foreground instead preserves its current event-specific detailed records byte-for-byte and in order before calling the handler. Accepted Connected/QR success restores retry count before channel publication/logging; exact foreground `QR code scanned successfully` follows accepted QR handling only, and managed mode never enters QR. Exported `BridgeHoldExit=78` is reserved for pairing-required, active-cooldown, QR-timeout, and startup-or-post-connect permanent-disconnect holds and does not restart-loop; Go runtime's panic-like status 2 remains restartable. The controller unit reads shared+controller only, explicitly unsets inherited `DATABASE_URL`, and launches exact resolved Node plus `%h/.local/share/whatsapp-session-controller/current/dist/src/main.js` with no `--preserve-symlinks-main`. Its fixed-safe guard realpaths both the module filename and `process.argv[1]`; direct invocation through `current` executes once, import remains inert, and Node resolves package and relative dynamic imports from the concrete immutable release selected at launch rather than a later `current` target. Pair bare metal only through a separately approved private foreground bridge run in an operator-only terminal with exact `BRIDGE_MANAGED=false BRIDGE_LOG_LEVEL=info`, never `debug`, and never redirect the QR to a journal/shared log; foreground logging and QR behavior are unchanged. For Compose initial/repair pairing, first start PostgreSQL, Redis, and controller with delivery disabled, run exact attached `docker compose run --rm --no-deps -e BRIDGE_MANAGED=false -e BRIDGE_NOTIFY_ENABLED=false -e BRIDGE_LOG_LEVEL=info bridge` while the namespace exists, require that command-local notification disablement to override conflicting `.env`, retain database/auth/session volumes, then start the managed bridge. Compose runs the bridge through a signal-forwarding entrypoint adapter that tracks trap interruption, waits again for actual child settlement, and maps real child `BridgeHoldExit=78` to container 0 only when `BRIDGE_MANAGED` is exact `true` under `restart: on-failure`. Exact `false` foreground pairing and an unset variable preserve 78 so `docker compose run` reports timeout/hold failure; panic-like child 2, every other nonzero status, and real 0 are preserved, and TERM/INT is forwarded. Compose has no portable infinite YAML stop duration; use the README's explicit `docker stop --time=-1 "$controller_id"` manual stop so `restart: unless-stopped` is suppressed while the controller drains indefinitely, then preserve the documented bridge/dashboard/transcriber/embedder/MCP stop followed by Redis/PostgreSQL stop order. Never use `docker compose down` during active work.

## Nonproduction verification

Use only non-sensitive fixtures and explicitly owned disposable services. Permitted static checks are TypeScript typecheck/build/tests, `shellcheck`/`bash -n`, `make -n`, Dockerfile parsing, `docker compose config` with dummy non-secret values, and `systemd-analyze verify` against copied temporary units with dummy absolute executables/environment files. Do not run `systemctl`, Compose `up/down`, Redis, cloud/model/auth operations, live databases, WhatsApp, Git writes, or credential reads during design/static validation.
